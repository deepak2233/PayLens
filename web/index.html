      Governance & audit

      Agents never write SQL — they run versioned, parameterized, row-capped templates, and every call is logged.

      Governance contract

      • No free-form SQL — versioned templates only, reviewed like code.
      • Bound parameters — every value bound; identifiers from a whitelist.
      • Row caps — bounded results, explicit truncation flags.
      • Full audit trail — agent, template, row count, duration per call.
      • Versioned metrics — success_rate v2 excludes unsettled attempts and reports pending share separately.
      • Fail-closed contracts — invalid events dead-lettered, never coerced.
      • Human approval — decisions stop short of autonomous mitigation.

          Sources
          
        
          Why this matters
          Real sources arrive with different vocabularies (Olist payment types like boleto, not_defined), their own edge cases (missing payments, approval-before-purchase clock skew, split payments, canceled orders) and checksum verification. The governed layer accepts them without schema drift — identical templates and agents, unchanged.
          
      
          
    
          

    
    
          
      
          Architecture
          Event flow and agent graph behind every number in this console.
          
      
          
        
          System flow
          Producer → transport → ingest → store → governed SQL → agents.
          
        
          
      
          
      
          
        
          
          
          Agent workflow (LangGraph)
          Supervisor routes by plan + material-drop signal; retry budget per agent.
          
          
          
        
          
        
          
          
          Layer map
          
          
            
            
          • Producers — synthetic generator (seeded hazards) or real adapters (Olist, Upworthy).
            • 
            
          • Transport — in-memory bus (demo) / Kafka (production); same consumer contract.
            • 
            
          • Ingest — dedup, reorder-safe stage derivation, late outcomes, dead-lettering.
            • 
            
          • Store — SQLAlchemy 2.0 on SQLite (demo) / PostgreSQL (Docker).
            • 
            
          • Governed SQL — template-only, parameterized, row-capped, audited.
            • 
            
          • Agents — supervisor + funnel / segment / anomaly / experiment.
            • 
            
          • Hybrid LLM — advisory planning + number-pinned narration; deterministic fallback, no API key needed.
            • 
            
          • Surfaces — FastAPI, CLI, this static console.
            • 
          
          
        
          
      
          
    
          

    
    
          
      
          Analyze your data
          Bring your own payments export — the same governed analysis (funnel, segments, anomaly timeline, A/B readout) runs right here in your browser. Nothing leaves your machine.
          
      
          
        
          1 · Schema
          
        
          One row per payment attempt. The window semantics mirror the governed pipeline: last 24 hours vs the previous 24 hours, so the file must span at least ~46 hours (two full days).
          
        
          
          
          ColumnRequiredValues
          
          
          attempt_idyesunique per attempt
          
          
          started_atyesISO timestamp (UTC) · span ≥ 46 h
          
          
          stage_reachedyesstarted · method_selected · initiated · succeeded · failed · pending
          
          
          statusnofallback stage source: succeeded / failed / pending
          
          
          method, gateway, bank, app_version, geo, customer_tiernofree text — become segment dimensions
          
          
          experiment_id, variantnoA/B columns (A/B) — enable the experiment readout
          
          
          amount, currency, customer_idnoamount in major units; customer_id pseudonymised — never PII
          
        
          
        
          
          
          Bigger files → CLI / API
        
          
      
          
      
          
        
          2 · Upload & run
          
        
          Entirely client-side — comfortable up to ~100 MB / 1 M rows. Larger volumes: run the same pipeline via python cli.py analyze --csv your.csv or POST /api/uploads (streaming, 200 MB cap, full audited trail).
          
        
          
          Drop your CSV here or click to choose a file
          
          one row per attempt · UTF-8 · , separated
