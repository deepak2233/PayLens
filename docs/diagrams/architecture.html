PayLens system architecture
Event path (1–3) and investigation path (4–5)
1  Capturepayment apps & gateway adapters

Checkout journeys emit one lifecycle event stream per attempt — started, method selected, initiated, gateway response, succeeded / failed — with pseudonymous customer ids, error codes and latency.

↓
2  TransportApache Kafka (KRaft)

Topics payment-events and experiment-exposures, 6 partitions keyed by attempt id. At-least-once delivery; analytics never runs inside the payment transaction path.

↓
3  Ingest & storePython consumers + PostgreSQL

Strict schema validation with dead-lettering, event-id de-duplication, monotone attempt-state derivation (out-of-order safe), delayed-outcome flags. Tables: attempts, events, assignments, deployments, metric_definitions.

↓
4  IntelligenceLangGraph supervisor + 4 agents
LangGraph supervisor — plans scope, branches on findings, retries with budget, checkpoints every run
Funnelwhere it drops
Segmentwho is affected
Anomalywhat changed
Experimentdid it help
↓
5  DeliveryFastAPI + analytics dashboard

Investigation report with numeric evidence and recommended actions; every figure links to its governed query, metric version and data window. Mitigation and rollout decisions stay with the bank team.

Governed SQL only — engineer-authored templates, bound params, read-only, row caps
Query audit log — agent, template, params, rows, duration, exact SQL per execution
Versioned metrics — success_rate v1 / v2; reports pin the version used
Hybrid reasoning — LLM plans and words; SQL + Python compute every figure
